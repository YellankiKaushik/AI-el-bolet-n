## Owner activation sequence

- [ ] Create/confirm the owner's Buttondown account and newsletter username. Verify sender/account approval and free-plan limits in that account. Keep all subscriber automations and real subscriber delivery off during acceptance. Import no third-party or unconsenting addresses.
- [ ] Keep double opt-in enabled. Use only an explicitly authorized mailbox you control to verify hosted signup, receipt of confirmation, and the transition from unconfirmed to active after you click the confirmation link. An HTTP success or mocked response is not mailbox delivery.
- [ ] Keep `BUTTONDOWN_API_KEY` only in private local configuration; never add it to Git, reports or a `VITE_` variable. The private Python adapter does not need a Vercel API token. `config.load_env()` must run in a private Python session if loading the key from `.env`.
- [ ] Use an already approved/exported public edition with a verified production permalink. Call `tools.buttondown_draft.create_draft(public_edition, PRIVATE_LEDGER)` deliberately. Retain one stable private ledger per edition/revision under ignored storage; it records the provider ID and reserves the action exclusively. Payload status is `draft`, with the exact `https://kaaush.vercel.app/newsletter/SLUG` permalink; it does not request subscriber sending.
- [ ] Inspect the draft/template in Buttondown, including actual source text, mobile layout, sender, permalink and unsubscribe footer. Keep recipient selection restricted to the authorized owner mailbox.
- [ ] For the adapter's single-mailbox acceptance set private `BUTTONDOWN_TEST_EMAIL` and temporarily `BUTTONDOWN_TEST_SEND_ENABLED=true`, then invoke `send_test(provider_id, PRIVATE_TEST_RESERVATION)` once. It requires a provider draft and sends the `recipients` array with exactly that one mailbox; it has no subscriber-broadcast operation. Alternatively use Buttondown's Preview → Send draft UI with the same single-mailbox restriction. Check the actual inbox/spam folder and rendered links. Disable the test flag afterward; do not declare DELIVERED from the API response alone.
- [ ] Verify unsubscribe with the owner's opted-in test subscription using the actual provider workflow. If a preview does not include a subscriber-specific unsubscribe link, test the subscription/preferences flow or perform a separately authorized owner-only subscriber acceptance; do not claim a generic draft preview proves list unsubscribe. Confirm the account shows the address unsubscribed and excluded from subscriber delivery before using a real list.
- [ ] Only after account, confirmation, inbox and unsubscribe acceptance, set public `VITE_BUTTONDOWN_USERNAME` in an isolated portfolio preview. Test the real hosted signup flow using the owner mailbox, then intentionally enable the same username in production via a reviewed deployment. Until then, leave it unset; the website displays subscriptions not activated. Username is public; the API key stays private.
- [ ] For the first subscriber newsletter, recheck human editorial approval, live permalink, provider status and the consented recipient list. The owner must explicitly choose delivery in the provider UI. Do not use status `sent` in a draft-creation request or add automated broadcast sending. A reader-only release does not authorize email delivery.

## Duplicate prevention and failure recovery

Creation reserves a private ledger with exclusive file creation before calling the provider. A timeout or unexpected response preserves the reservation and blocks blind retries; reusing the same ledger cannot create another draft. The single-mailbox send likewise reserves a private file and requires an existing draft. Preserve these files across restarts and use consistent paths, rather than inventing a new ledger to bypass the duplicate guard.

For a known provider ID call `reconcile(provider_id)` (GET) and inspect the provider dashboard/history. If the ID was lost during an uncertain creation response, locate the draft by subject/canonical permalink and confirm its identity in the provider UI before recording it privately. Never delete the reservation and retry merely because a response was lost. If queued, sent or uncertain, investigate before any further send; local timeout is not proof of provider failure. Treat 401/403 as account/token/entitlement problems, 429 as a rate-limit response and network/5xx timeouts as potentially ambiguous. Correct the cause and reconcile without duplicating a publication. Do not print provider credentials or recipient data into public logs.

The existing six portfolio Python test methods cover mocked provider drafts, duplicate reservations, uncertain failures, one-mailbox gating and approval/export rules. They do not verify Buttondown account entitlement, deliverability, consent state or real unsubscribe behavior. Those boxes remain unchecked until the owner completes live acceptance.
